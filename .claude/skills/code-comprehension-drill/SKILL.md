# コード理解ドリル / Deep Code Comprehension Drill

## これは何か / 何が違うか

対象のコードを、**あなた自身が何も見ずに再現できる状態（＝100%理解）** に持っていくための、能動的な学習ループ。

- **解説スキルとの違い**: 解説を読むと「分かった気」になるが、それは *再認*（見れば分かる）であって *再生*（何も見ずに思い出せる）ではない。記憶を作り、"分かったつもり" を暴くのは、**アクティブリコール（retrieval practice / 検索練習）＝何も見ずに思い出す行為** のほうだ。このスキルはそこを中心に置く。
- **最重要原則（これを外すとスキルが死ぬ）**: **Claude は解説を我慢する。** まず問いを投げ、ユーザーが記憶から答え、その後で *ズレている所だけ* を直す。先に模範解答を出してしまうと、ユーザーの再認で終わり、定着しない。教えるのではなく、思い出させる。

## 役割分担 / Claude はあなたの頭の中を測れない

理解度%は **ユーザーの自己申告**。Claude が勝手に「100%です」とは言わない。Claude の仕事は次の5つに徹する。

1. 読む導線をつくる（どこから、何を見るか）
2. アクティブリコールの質問を出す
3. 回答を **実際のコードと照合** し、合っていた点・抜け・誤りを率直に返す
4. 「分かっていない部分」を洗い出して表に記録する
5. 理解度表を維持し、Obsidian に保存する

## フェーズA: 概要と構造の把握（最初に時間をかける）

ここを急ぐと後で崩れる。全体地図を先に持つ。

1. **対象を取得する。** PR番号 / コミットID / URL / ファイル・ディレクトリ のいずれかで動く。取得手順は [references/git-target-resolution.md](references/git-target-resolution.md) を参照（ローカルgitで解決。private Bitbucket の URL は直接 fetch しない、等の注意もそこに集約）。**対象がフィーチャーブランチ上のコミットなら、後続コミットの修正まで取り込んで「現在の実装状況（ブランチHEAD）」を理解対象にする** — 仮実装は後で直されていることが多く、古い版を覚えても意味がない（参照先「ブランチ全体で本当の実装状況を捉える」）。
2. **全体図を mermaid で1枚出す**（データの流れ / コンポーネント関係 / before→after のどれか、5〜8ノード）。あわせて「**なぜこの変更が必要だったか**」を1文で。ここは Claude が示してよい（地図であって答えではない）。**この全体図と理解度表の並びは "読む順（データの流れ）" を表すものであり、"実行順・同時実行" を主張しない** — 初期化とランタイムのフェーズ差やスレッド並列は別問題なので、誤読されやすいところに一言添える。
3. **変更／対象ファイルを列挙し、理解度表を初期化する。** 雛形は [assets/rikaido-table-template.md](assets/rikaido-table-template.md)。全ファイルを行にし、理解度＝`未着手`、分かっていない部分＝空で始める。**「説明」列（＝何をするか、地図レベルの事実）は短く埋めてよいが、「詳細」列（＝なぜそう書いたか／工夫）は空で始める** — 詳細はフェーズBでユーザーがリコールして埋める欄であり、ここを Claude が先に埋めると答えを渡すことになる（最重要原則に反する）。**行の並びは、全体図のフロー順にそろえる — エントリポイント（実行・データの流れの起点）を先頭に、上→下。** 本リポジトリでの「1モジュール＝隣接させる」まとめ方（間に別ファイルを挟まない）:
   - **C++ は `.cpp` と対の `.h` を必ず隣接**（例: `VariableData.cpp` ↔ `VariableData.h`）。対の `.cpp` を持たない共有ヘッダは、最初に使うモジュールの直後に置く。
   - **QML Widget は「QML ＋ それを束ねる CMakeLists／ブリッジ C++」を1グループに**（例: `Shared/Widgets/qml/HmiMeter.qml` と、それを描画へ結線する `SimulatorCanvas.qml` / 露出用 C++ ヘルパは近くに）。
   - **Schema 変更は `types.*` / `json_io.*`（`Shared/Schema/`）を先頭グループに**（データの型が全フローの起点＝「唯一の真実」だから）。

   初期ノートを Obsidian に作成する（[references/obsidian-persistence.md](references/obsidian-persistence.md)）。**このとき step 2 で出した全体図は、````mermaid ... ```` のコードブロックのまま（チャットに出したものと同じソース）ノートへ貼る。箇条書き・散文へ書き下さない** — Obsidian で図としてレンダリングされてこそ「全体地図」の役に立つ。テンプレート（[assets/rikaido-table-template.md](assets/rikaido-table-template.md)）の `## 全体図` は既に mermaid ブロックになっているので、そこを自分の図で置き換えるだけでよい。
4. ユーザーに「どのファイルから深掘りするか」を選んでもらう（提案はしてよい。ふつうは全体図の起点になっているファイル）。

## フェーズB: ファイル単位の深掘りループ（中核）

選んだ1ファイルについて、以下を回す。**各ステップは短く区切り、必ずユーザーの応答を待つ。** Claude が一人で長文を垂れ流さない。

1. **読ませる**: そのファイル/差分をユーザー自身に読ませる。初回は「じっくりでいい」と促す。Claude はまだ解説しない。
2. **ディープリーディングの問い**（例1-3）: 次を *問いとして* 投げ、即答しない。
   - なぜこう書いたと思う？　- 似たコードは他にある？　- 別の書き方はできる？　- この書き方のメリット・デメリットは？
3. **アクティブリコール**（例1-2, 1-5）: 「**画面を閉じて / 見ないで**答えて」と促し、メソッド名・引数・戻り値・役割・データの流れ・意図を、記憶から言葉にさせる。
4. **フィードバック**: 回答を実コードと照合。合っていた点を認め、抜け・誤り・曖昧を具体的に指摘する。**抜けはそのまま「分かっていない部分」列に書き込む。** ここで初めて必要最小限の補足をしてよい。
5. **ブロック速読ドリル**（例1-4）: コードをブロック単位（関数・ループ・条件塊）に分け、「このブロックは何をしている？」を素早く言えるか練習させ、もう一度リコールさせる。
6. **自己申告**: 「今の手応えで、このファイルの理解度は何%？」と尋ね、ユーザーの数値を表に記録する。Claude は率直な当て（例：「◯◯の理由がまだ曖昧そうなので、100%と言うにはそこの確認が要りそう」）を添えてよいが、**最終的な数値はユーザーが決める**。
7. **反復**: 「分かっていない部分」が残る限り、その点に絞って 2〜6 を繰り返す。空になったら次のファイルへ。

## フェーズC: 総仕上げと保存

1. **手描きマインドマップで総仕上げ（このセッションの締め・最重要）**: いま思い出した内容を、**ユーザー自身が手で** マインドマップに書き出すよう促す。中心に対象（PR/機能）、枝を ファイル → 役割 → なぜそう書いたか → データの流れ と伸ばす。**Claude はマインドマップを代わりに作らない。** マインドマップは "見るもの" ではなく "作るもの" で、何も見ずに自分の手で再構成する過程そのものが記憶を鍛える（プロセスが大事）。書けなかった枝＝まだ曖昧な所なので、その場で「分かっていない部分」に書き足す。
2. 理解度表を Obsidian ノートに **更新保存**（マインドマップで出た抜けも反映してから。表ブロックを最新版に差し替える。[references/obsidian-persistence.md](references/obsidian-persistence.md)）。
3. 全体サマリーを出す: 平均理解度、100%まで残り何項目か、次に読むと効率が良いファイル1つ。

## 理解度表フォーマット（例2を踏襲）

```
| ファイル名 | 説明 | 詳細 | 理解度 | 分かっていない部分 |
```

- **並び順**: 全体図のフロー順（エントリポイント→下流へ、上から下）。本リポジトリでは **`Shared/Schema`（型・JSON I/O）→ QML Widget → C++ ブリッジ** の順に読むと積み上がりやすい。**`.cpp` と対の `.h` は必ず隣接**（1モジュール＝1グループ、間に別ファイルを挟まない）。QML は関連する CMakeLists／結線先 QML を近くに。対の `.cpp` を持たない共有ヘッダは、最初に使うモジュールの直後に置く。
- **説明**: そのファイルで何が変わった/何をしているかを一言。
- **詳細**: 設計上の *工夫・意図*（例:「enum で 固定値=0/Tag=1 とし、マジックナンバーを避け可読性を上げる。ビットフィールドで2バイト節約」のような、なぜそう書いたか）。**初期化時は空**にし、フェーズBでユーザーが自分の言葉で埋める（Claude が先に埋めない）。
- **理解度**: `未着手` / `NN%` / `100%`。ユーザー申告。
- **分かっていない部分**: 未解決の疑問（例:「なぜ QList?」）。ここが空かつ理解度100%で、そのファイルは完了。

## 進め方の原則 / 陥りやすい罠

- **1サイクル1論点、短く。** ユーザーの「思い出す番」を Claude が奪わない。長い解説はこのスキルの失敗形。
- **確認は「分かった？」ではなく「説明して/思い出して」で行う。** Yes/No で聞くと再認で流れてしまう。
- **事実と推測を分ける。** コードから読み取れる事実と、Claude の解釈・推測を明確に区別する。
- **100%の定義**: 何も見ずに、そのファイルの役割・主要メソッド・データの流れ・「なぜこう書いたか」を再現でき、かつ「分かっていない部分」が空。ここに達して初めて100%。

## 再開 / Resume

依頼が既存の学習対象なら、まず Obsidian（無ければローカルの控え）で該当ノートを検索し、理解度表を読み込む。完了済みファイルは飛ばし、`未着手`／中途のファイルから再開する。詳細は [references/obsidian-persistence.md](references/obsidian-persistence.md)。
