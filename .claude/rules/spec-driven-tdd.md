本番コード（C++ / QML のロジック）を新規作成・変更するときは、**仕様 → テスト → 実装** の順で進める。仕様の置き場所は [Docs/requirements/](../../Docs/requirements/README.md)（要件 `REQ-` と受け入れ条件 `ACC-`）。

| 段階 | やること | 次へ進む条件 |
|---|---|---|
| ① 仕様 | 変更に当てはまる `REQ-` と `ACC-` を探す。無ければ仕様書に足す | 受け入れ条件が、テストで確かめられる文になっている |
| ② テスト | 受け入れ条件ごとに、テストを 1 本以上書く | `ctest` で新しいテストが**アサーション失敗**する（コンパイルエラーは数えない） |
| ③ 実装 | テストには触らずに、本番コードを書く | `ctest` が全件成功する |
| ④ 仕様の更新 | 仕様書の状態を「実装済」にし、索引の件数を直す | [requirements/README.md](../../Docs/requirements/README.md) の表と合っている |

- **不具合の修正**：まず、不具合を再現するテストを書いて失敗を確かめ、そのあとで直す。
- **振る舞いを変えないリファクタリング**：先に、今の挙動を固定するテストを書いて成功を確かめる。リファクタリングのあとも、同じテストが成功すること。
- ③ でテストが間違っていると分かったら、テストを直さずに ① か ② に戻る。
- テスト名か、テストの直前のコメントに、受け入れ条件の番号（`ACC-DAT-001` など）を書く。どの仕様のテストかが追える。
- 新しい機能は、**承認前の候補を勝手に始めない**。仕様に足す前に、ユーザーと範囲を決める（[phase-status.md](../../Docs/phase-status.md)）。
- ドキュメントだけの変更や、ビルド設定だけの変更には適用しない。

**Why:** ユーザーが 2026-11-23 に、契約による設計（DbC）を取りやめ、一般的な仕様駆動 + TDD にしたいと明示した。要求仕様書（`REQ-` / `ACC-`）がすでにあるので、それを土台にする。

**How to apply:** 本番コードを触る前に ① を済ませる。② の失敗確認は省略しない。
