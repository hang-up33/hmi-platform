# QML モジュール規約

- すべての QML モジュールは `qt_add_qml_module` で **明示的に `URI` を付与**（`HmiEditor` / `HmiSimulator` / `HmiWidgets`）。
- `Shared/Widgets` は `OUTPUT_DIRECTORY ${CMAKE_BINARY_DIR}/HmiWidgets` を指定し、ビルドパスを URI と一致させる（Qt の警告防止）。
- QML ロードは `loadFromModule(URI, "Main")` を使用し、`qrc:` パス指定は避ける。
- QML import は Qt6 形式（`import QtQuick` — バージョン番号無し）。
- **QtQuick 標準型と同名の QML ファイルを作らない**（`Canvas.qml` / `Rectangle.qml` / `Item.qml` / `Text.qml` / `Image.qml` / `Window.qml` / `Button.qml`〔Controls〕等）。`import QtQuick` だけでは標準型が優先解決され、`Cannot assign to non-existent property` 等のエラーになる。回避策はいずれか：
  - **プレフィックス命名**（推奨）：`EditorCanvas.qml` / `HmiButton.qml` のように接頭辞を付ける。
  - **自モジュールを明示 import**：`Canvas.qml` のような名前を採用した場合、利用側 QML に `import HmiEditor`（または `HmiWidgets`）を必ず記述する。
- 共有 Widget（`HmiWidgets`）を新規追加する際は、上記の命名衝突に特に注意する（`Button` / `Label` / `Slider` 等は Controls と衝突しうる）。
- **QML singleton（`pragma Singleton`）は CMake 側でも `QT_QML_SINGLETON_TYPE TRUE` を立てる**（Task 39 で `VariableStore` 追加時に踏んだ）。`pragma Singleton` を書いて `QML_FILES` に足すだけでは **qmldir に singleton 登録されず**、利用側で `VariableStore.foo()` が「Property 'foo' of object VariableStore is not a function」になる（型参照に解決されメソッドが見えない）。`qt_add_qml_module` の **前** に `set_source_files_properties(qml/VariableStore.qml PROPERTIES QT_QML_SINGLETON_TYPE TRUE)` を置く。singleton は状態がテスト間で共有されるため、Qt Quick Test では `init()` でリセット（例：`VariableStore.clear()`）してから検証する。
- **データバインディング（変数 → widget プロパティ追従）は「関数経由でも QML の依存追跡が効く」ことを使う**（Task 41 で確立）。Simulator/Runtime（読み取り専用の実行側）で binding（`{property, variable}` 配列）を解決するとき、delegate に `function boundValue(prop){ ... return VariableStore.values[v] }` を置き、プロパティ側を `text: { const v = wrapper.boundValue("text"); return v !== undefined ? String(v) : 静的値 }` のように **関数を呼ぶバインディング式**で書く。**関数評価中に読んだ `VariableStore.values`（プロパティ）は依存として追跡され、`VariableStore.setValue`（= values 再代入）で式が再評価される**ため、`Qt.binding` を動的生成しなくても「変数変化 → property 追従」が成立する。アクション実行（`setVariable`/`toggleVariable`）は HmiButton の `onClicked` から `VariableStore.setValue/toggle` を呼ぶだけ。変数の型は Project レベル定義（`variableModel`）から引いて coerce する。**この経路は SimulatorCanvas（= Runtime 共有ソース）に閉じ、選択/編集は持ち込まない**（読み取り専用原則を維持）。Phase 5 で新 Widget 種別を足すときも同じ `boundValue` パターンを delegate に踏襲すれば binding が再利用できる。SimulatorCanvas には `widgetItems` alias が無いため、QML テストは再帰 `objectName` 探索（`widget_<id>` / `hmiButton`）で delegate を辿る。
- **複数バイナリ間で共有する QML モジュールは `STATIC` でビルドし、利用側アプリで plugin ターゲットをリンクする**。これは Qt 公式の「Multiple QML Modules in One Binary」推奨構成：
  - 共有側（`Shared/Widgets/CMakeLists.txt`、`Simulator/CMakeLists.txt` の `hmi_simulator_qml`）：`qt_add_qml_module(<name> STATIC URI <Uri> ...)`
  - 利用側（`Editor` / `Simulator` / `Runtime`）：`target_link_libraries(<app> PRIVATE <name>plugin)`
  - 動的ビルド（`STATIC` を付けない）だと plugin が `MODULE_LIBRARY` になり `target_link_libraries` がエラーになる。
  - **単一バイナリ専用** の QML モジュール（例：`HmiEditor` URI）は実行ファイル直結（`qt_add_qml_module(hmi_editor URI HmiEditor ...)`）のままで OK。STATIC 化は別バイナリと共有する場合のみ必須。
  - 代替として利用側で `IMPORTS HmiWidgets` を宣言する書き方もあるが、本プロジェクトの Qt 6.11（Homebrew）構成では自モジュール（`HmiEditor`）のリソース解決と競合して `No module named "HmiEditor"` で起動失敗した実績がある。STATIC plugin + 直リンクが唯一動作確認済みの方法。
  - Yocto / i.MX8MP の組み込みデプロイでも静的リンクの方が dylib 配布パスの問題を避けられて好都合。
- **`default property alias content: <inner>.data` で受けた子要素の `parent` は内部 Item を指す**。たとえば `EditableWidget` は内部 `container` に子を流し込むため、Main.qml で `EditableWidget { HmiButton { text: parent.widgetText } }` と書くと `parent` は `container` を指してしまい、`widgetText`（root のプロパティ）が undefined になる。回避策：外側 Item に `id` を付け、子からは `id` 経由で参照する（例：`EditableWidget { id: btn; HmiButton { text: btn.widgetText } }`）。Canvas.qml も同じ構造のため同様の注意が必要。
- **`drag.filterChildren: true` の MouseArea 下では、親の `onClicked` はクリックでは発火しない**（Task 25 で確認）。`EditableWidget` の `dragArea` は `drag.filterChildren: true` で子（`HmiButton`）の `clicked` を活かしつつドラッグ閾値超過時だけ grab を奪う設計のため、純クリックは**子 MouseArea が消費**して親まで届かない。よって「クリックで選択」のような操作は**子 Widget の `clicked` を中継**して実現する（`HmiButton { onClicked: wrapper.selectRequested(wrapper.widgetId) }`）。選択状態の所有は `Canvas` に集約する。**Task 36 で選択は単一 id から集合 `selectedWidgetIds`（id 配列）へ拡張**：真実は `selectedWidgetIds`、`selectedWidgetId` は **ちょうど 1 個選択のときだけ非空の readonly 派生**（単一プロパティ編集 / 削除引数既定に使う）。QML の `id` はファイルを跨げないため `EditableWidget` には plain な `selected`(bool) ＋ `signal selectRequested(string requestedId, int modifiers)` だけを持たせ、結線（`selected: root.selectedWidgetIds.indexOf(widgetId) >= 0` / `onSelectRequested: root.selectWidget(requestedId, modifiers)`）は `root` が可視な delegate 側（`Canvas.qml`）で行う。**Shift / Ctrl クリックの加除のため `HmiButton.clicked(int modifiers)` で modifiers を中継**する（`MouseArea.onClicked: function(mouse){ root.clicked(mouse.modifiers) }`。Simulator は clicked 未接続なので影響なし）。`Canvas.selectWidget(id, modifiers)` が `modifiers & (Qt.ShiftModifier|Qt.ControlModifier)` で加除 or 単一置換を判断。背景クリックでの解除は `background` に置いた MouseArea（widgetLayer より**前**に宣言し、Widget 上のクリックは子が消費・空き領域だけが落ちてくる構造）で `selectedWidgetIds = []`。**一括ドラッグ移動**はドラッグ中の「リーダー」Widget の `dragging`/`x`/`y` 変化を delegate の `Connections` が購読し、Canvas が他の選択 Widget へ同じ差分を適用する（siblings は `dragging=false` でガードしフィードバックループを防ぐ）。新しい Widget 種別を `EditableWidget` でラップする時もこの結線パターンを踏襲する。
- **undo / redo は「状態スナップショット方式」で QML 完結**（Task 38）。`Canvas` が `undoStack`/`redoStack`（各要素 = `snapshotModel()` の配列＝その時点の全 Widget 状態）を持つ。**構造変更（追加/削除/ペースト/整列/分布）は操作の直前に `pushUndo()`** で前状態を積む（`redoStack` はクリア）。**連続操作（ドラッグ/リサイズ/インスペクタ編集）は `beginEdit()`〔開始時に前状態を保留〕→ `commitEdit()`〔確定時に状態が実際に変わっていれば 1 件積む・no-op は捨てる〕** で「中間フレームを積まず確定時のみ 1 件」にする。境界の結線：ドラッグ = delegate の `Connections.onDraggingChanged`(true)→`beginEdit` / `onDragFinished`→`commitEdit`、リサイズ = `EditableWidget` の `resizeStarted`/`resizeFinished` signal → delegate で `beginEdit`/`commitEdit`、インスペクタ = `Main.qml` の `onInspectorFieldFocusedChanged`(フォーカス得喪)→`beginEdit`/`commitEdit`。`undo()`/`redo()` は配列を **再代入**（push でなく concat/slice）してバインディング（`canUndo`/`canRedo`）へ通知し、復元時は `selectedWidgetIds = []` で stale 選択を避ける。プロジェクト読込時は `clearHistory()`。新しい編集操作を足す時も、この「構造変更=pushUndo / 連続操作=begin・commit」の境界則に合わせる。
- **インスペクタ等で「選択中の live Item を `TextField` から two-way 編集」する時は `onTextEdited`（書き戻し）＋ `Connections.onSelectedItemChanged`（表示更新）の 2 本立てにする**（Task 26 で確立）。`text:` を選択 Item のプロパティに**直接バインドしてはいけない**：ユーザーがキー入力するとそのバインディングが切れ、以後の選択切替で表示が追従しなくなる。正しいパターンは (1) `TextField.onTextEdited`（**ユーザー入力でのみ発火**、プログラム変更では発火しない）で `selectedItem.widgetText = text` と live Item へ書き戻す → `HmiButton { text: wrapper.widgetText }` が即追従、(2) `Connections { target: rootWindow; function onSelectedItemChanged() { field.text = selectedItem ? selectedItem.widgetText : "" } }` で**選択が変わった時だけ**表示値を更新。編集対象の解決は `Canvas` の `selectedWidgetId` と `widgetItems`(=`widgetLayer.children`) を引数に取る純関数バインド（`property var selectedItem: resolveSelectedItem(canvas.selectedWidgetId, canvas.widgetItems)`）にすると、選択変更でも delegate 再生成（children 入替）でも同一 id の新しい Item に解決し直せる（Phase 4 設計指針「live Item を真実に・var 配列据え置き」と整合）。T27/T29 のインスペクタ項目（座標・サイズ・スタイル）も同じ 2 本立てで足す。
- **数値フィールド（座標・サイズ）は `SpinBox` でなく `TextField` + `IntValidator` を使う**（Task 27 で確立）。`QtQuick.Controls` の **editable な `SpinBox` は `value` をプログラムから設定しても表示テキストが更新されない不具合**があった（Windows / Qt 6.11 で確認：`value` は正しく入っているのに入力欄が空表示。X/Y/幅 は出るのに高さだけ空、という再現性のない壊れ方をした）。`TextField { validator: IntValidator { bottom: N; top: M }; onTextEdited: if (acceptableInput) item.<prop> = parseInt(text) }` なら表示を自前で制御でき確実。値の表示同期は上記 2 本立て + **選択中 Item の `xChanged`/`widthChanged` 等を購読する `Connections { target: canvas.selectedItem; ... }`**（drag/handle 由来の変化に追従）。ただし **同期関数は `activeFocus` のフィールドを上書きしない**こと（書き戻し→幾何変化→同期 でテキスト再代入するとカーソルが飛ぶ）。`acceptableInput` で妥当値のみ書き戻し、最小サイズは `IntValidator.bottom` と `EditableWidget.minWidth/minHeight` を一致させる。**ただし `editable: false`（既定）の `SpinBox` は `value` をプログラム設定しても表示が正しく更新される**ので、文字サイズのような「ユーザーが矢印ボタンで増減する数値」には素直に使える（Task 29 の `inspectorFontSizeSpin` は `editable` を付けず `value` 設定で表示同期できた）。書き戻しは `onValueModified`（ユーザー操作でのみ発火、プログラム代入では発火せず書き戻しループを起こさない）、表示同期は `Connections.onSelectedItemChanged` で `value` を更新する 2 本立てにする。壊れるのは **`editable: true` の SpinBox** だけ。
- **インスペクタは折りたたみセクション（`Editor/qml/InspectorSection.qml`）で構成する**（Task 44〜45 で確立）。`Main.qml` の単一選択フォームは **基本 / 文字 / 背景・枠 / 状態 / 動作 / 詳細（既定で閉）** の `InspectorSection`（ヘッダ ▼/▶ クリックで開閉、`default property alias content` で子を内部 Column へ流し込む。`leftPadding` は `QQuickBasePositioner` のネイティブプロパティで Column でも効く）に分かれる。**新しい Widget プロパティの編集 UI を足すときは、平坦に append せず意味の合うセクション内に置く**（色 → 背景・枠、文字関連 → 文字、状態 → 状態、技術的/通常編集しない項目 → 詳細）。ラベルは**直訳でなく動作ベースの語**にし（例：`checkable`→「トグルボタンにする」）、意味が伝わりにくい項目には `ToolTip.text` + `ToolTip.visible: hovered` + `ToolTip.delay: 600` で 1 行補足を付ける。セクション化・リネーム・ToolTip はいずれも **表示層のみ**で objectName・編集ロジック（上記 2 本立て）・Schema・round-trip は変えない（E2E は `objectName` 解決のため不変必須。`git diff` で objectName 削除 0・id 一致を確認する）。Phase 5 で新 Widget 種別を足すときも同じセクション構成へ項目を追加する。
- **プロジェクト読込で複数の state を設定する順序に注意**（Task 40）。インスペクタの sync（`Connections.onSelectedItemChanged`）が、別の state（変数定義リスト等）に依存する ComboBox の選択肢を引くとき、**依存元を先に設定する**。具体例：読込ハンドラで `canvas.widgetModel = ...` を先に設定すると、その変更が `selectedItemChanged` を発火させ、アクション target / バインディング variable の ComboBox 選択肢（`variableNameModel()` ＝ `projectVariables` 由来）がまだ空のまま sync され「(未選択)」に落ちる。**`rootWindow.projectVariables` を `widgetModel` より先に代入**して選択肢を揃えてから model を差し替える。動的 Repeater 由来の入力欄（変数パネル等、id 固定できない）の Delete ショートカット抑止は、各行の `onActiveFocusChanged` で増減する `property int variableFieldFocusCount` を `inspectorFieldFocused` に OR する。
- **リサイズハンドルは `EditableWidget` に専用 `MouseArea` + `preventStealing: true` で実装する**（Task 27）。親 `dragArea`（`drag.filterChildren: true` で Widget 移動）にハンドルの press を奪われると「リサイズのつもりが移動」になるため、ハンドル側 MouseArea に `preventStealing: true` を立てて握り続ける（ハンドルは `dragArea` の子ではないので本来奪われないが安全側で固定）。座標は `mapToItem(root.parent, mouse.x, mouse.y)` で widgetLayer 基準に変換し、press 時点との差分で `root.width/height` を更新する（ハンドルが resize で動くため、ハンドル相対座標だと値が暴れる）。`Math.max(minWidth, ...)` で最小 clamp。
- **C++ ヘルパーを QML に公開するときは `setContextProperty` が最も軽い**。Editor 側に存在する一時的なコントローラ（例：`ProjectIo`）は `engine.rootContext()->setContextProperty("projectIo", &io)` でグローバル変数として QML から呼べる。`qmlRegisterType` / QML_ELEMENT は型インスタンス化が必要な場合に使う。**`hmi_schema` 等の Shared ライブラリは QML を一切知らないことを保ち**、QML 連携クラスは利用側アプリ（Editor / Simulator）に置く。
- **Editor / Simulator で同等の C++ ヘルパー「クラス」が必要になる場合、Shared に移さず両方に独立して持つ**（Task 8 で確立）。Editor `ProjectIo`（save + load）と Simulator `ProjectLoader`（load のみ）は load() の骨格（ファイル読込→parse→`isValidJson`→先頭 screen 取得）がほぼ同一だが、責務（編集 vs 読み取り専用）が異なるため**クラス自体は統合しない**。クラスの Shared 昇格を検討するのは、save 側にも同等の機能差が現れた時のみ。**ただしリファクタリングで重複の核は Schema へ寄せた**：①「Schema 型 ⇄ QVariantMap のフィールド転写」は Schema 型自身（`WidgetData::toVariantMap`/`fromVariantMap` 等）へ、②「JSON パース + 検証」は `ProjectData::parseValidated(QByteArray)→std::optional<ProjectData>`（「`isValidJson` を通してから `fromJson`」を 1 箇所に強制）へ集約済み（[[schema-conventions]] 参照）。両クラスはそれらを呼ぶだけ。残るのは **ファイル / QUrl の OS I/O（`toLocalFile` + `QFile` 読込）と QML 向け結果マップ組み立て**のみで、これは利用側アプリの責務として「重複を許容、利用側完結」で据え置く（Schema に QFile を持ち込まない）。
- **Simulator と Runtime はソース完全共通**（Phase 3-B / Task 22 で確立済み）。Editor との関係（独立保持）とは別に、Runtime は Simulator/ のソースを `Runtime/CMakeLists.txt` の CMake glue で再利用して `hmi_runtime` バイナリを生成する。Runtime/ には `.cpp` / `.qml` / `.h` を置かない。Runtime に追加機能が必要な場合も Simulator/ 側で編集し、必要なら `#ifdef HMI_RUNTIME_BUILD` で振る舞いを分岐する。QML モジュール URI も Simulator と同じ `HmiSimulator` を再利用する（モジュール名を変えるとソース共有が崩れる）。詳細は [Docs/phase3b-runtime-plan.md](../../Docs/phase3b-runtime-plan.md)。
- **ソース共有の具体的 CMake 技法は「共通 function + `CMAKE_CURRENT_FUNCTION_LIST_DIR`」を採用**（Task 22 で確立）。`Simulator/CMakeLists.txt` で `function(hmi_add_simulator_like_executable target)` を定義し、関数内で `qt_add_executable(${target} ${CMAKE_CURRENT_FUNCTION_LIST_DIR}/src/main.cpp ...)` のように **関数定義位置のディレクトリ** を絶対パス基準にする。`Runtime/CMakeLists.txt` は `hmi_add_simulator_like_executable(hmi_runtime)` の 1 行だけ。CMake function はグローバルスコープなので、ルート `CMakeLists.txt` で `add_subdirectory(Simulator)` を `add_subdirectory(Runtime)` より **前** に置く必要がある（順序を逆にすると関数未定義エラー）。`CMAKE_CURRENT_FUNCTION_LIST_DIR` 自体は CMake 3.17+ で導入された機能だが、**本リポジトリは root `CMakeLists.txt` で `cmake_minimum_required(VERSION 3.21)` を指定しているため、Yocto SDK 側の CMake は 3.21 以上が必須**（3.17〜3.20 だと configure 時点で落ちる。Task 23 着手時に SDK の `cmake --version` を確認する）。QML module 側は同じ Simulator/CMakeLists.txt で `qt_add_qml_module(hmi_simulator_qml STATIC URI HmiSimulator ...)` として STATIC plugin 化し、function 内の `target_link_libraries` で両バイナリに `hmi_simulator_qmlplugin` を取り込む（CLAUDE.md 既出の Shared/Widgets と同パターン）。実行ファイルに直結したまま QML module を宣言した状態では別バイナリから共有できないため、STATIC 化は必須。
- **Task 22 時点では `hmi_runtime` のウィンドウタイトル・applicationName は `hmi_simulator` と同じ**（[Simulator/qml/Main.qml](../../Simulator/qml/Main.qml) の `Window.title = "HMI Simulator"`、[Simulator/src/main.cpp](../../Simulator/src/main.cpp) の `setApplicationName("hmi_simulator")`）。これは計画書「Task 22 段階では分岐ゼロのまま、Task 24 で実機差異が見えてから `#ifdef HMI_RUNTIME_BUILD` を入れる」方針に従った意図的な現状。Task 24 で実機初期化を入れる時に分岐すれば良い。Codex レビューでウィンドウタイトルが Simulator のままなことを指摘されたら本方針を根拠に説明する。
- **Simulator のような起動時自動ロード機能が欲しい時は CLI 引数 + `setContextProperty` の組み合わせが軽い**（Task 8 で確立）。`main.cpp` で `QCommandLineParser` から取った `QUrl` を `initialJsonUrl` 等の名前で context に詰め、QML 側 `Component.onCompleted` で空判定して `projectLoader.load()` を呼ぶ。これは FileDialog の自動操作が AppleScript で不可能な問題（[screenshot-capture](../skills/screenshot-capture/SKILL.md) スキル参照）を回避する正攻法でもある。
- **QtQuick.Controls / QtQuick.Dialogs は QML `import` だけで動く**（Qt 6.5+）。CMake で `Qt6::QuickControls2` 等を明示リンクしなくても plugin が動的にロードされるため、`target_link_libraries` への追加は不要。デプロイ時のみ `windeployqt` / `macdeployqt` で plugin 同梱を確認する。
- **`FileDialog.selectedFile` は `file:///...` 形式の `QUrl`**。C++ で受けるときは `QUrl::toLocalFile()` で OS パスに変換してから `QFile` / `QSaveFile` に渡すこと（`toString()` だと `file://` が残って書き込みに失敗する）。書き込みは `QSaveFile` を使い `commit()` で原子的に保存するのが安全。
- **Widget のスタイル属性（色・フォント等）は「未指定 = 空文字 / 0」を許す入力プロパティ + `readonly resolved*` フォールバックで HmiButton に既定値を集約する**（Task 28 で確立）。`property color backgroundColor: "#4cc9f0"` のように public プロパティを `color` 型 + 既定値で持たせると、delegate が未指定の空文字 `""` を代入したとき color が invalid（黒）になり既定外観が壊れる。正しいパターンは (1) public 入力は `property string backgroundColor: ""` / `property int fontSize: 0`（空 / 0 = 未指定）にする、(2) `readonly property color resolvedBackgroundColor: backgroundColor !== "" ? backgroundColor : "#4cc9f0"`・`readonly property int resolvedFontSize: fontSize > 0 ? fontSize : 14` で既定外観を **HmiButton 1 箇所だけに** 置く、(3) 描画（`color` / `font.pixelSize` / press の `Qt.darker(resolvedBackgroundColor, 1.2)`）は `resolved*` を参照する。これにより Editor（`Canvas.qml`）/ Simulator（`SimulatorCanvas.qml`）両 delegate は既定値を二重定義せず、モデル値（空可）を素通しで渡すだけでよい（`backgroundColor: wrapper.widgetBackgroundColor`）。Schema 側も既定値（空 / 0）は `toJson` で省略書き出しして後方互換を保つ（[schema-conventions](schema-conventions.md)）。**レイヤ貫通順は Schema → QML delegate → HmiButton**。**C++ ブリッジ（`ProjectIo` / `ProjectLoader`）の手書き `QVariantMap` コピーはリファクタリングで廃止**し、転写は `WidgetData::toVariantMap`/`fromVariantMap`（Schema）へ集約した（[[schema-conventions]]）。よって今後 Widget スタイル属性を増やす時は **①Schema 型（`toJson`/`fromJson`/`toVariantMap`/`fromVariantMap` の 4 メソッド＝同一 .cpp）②delegate（`Canvas.qml` / `SimulatorCanvas.qml`）③`EditableWidget` のメタ ④`HmiButton` の入力 + `resolved*`** を揃える（C++ ブリッジ 2 ファイルは変更不要になった＝「一番取りこぼしやすい箇所」を解消）。delegate と HmiButton だけ直して Schema の `toVariantMap`/`fromVariantMap` を忘れると JSON の値が描画に届かない点は従来同様注意する。
- **テキスト配置（`horizontalAlignment` / `verticalAlignment`）を効かせるには `Text` を `anchors.fill: parent` にする**（Task 34）。`anchors.centerIn: parent` のままだと `Text` は内容サイズに縮み常に中央に置かれるため、alignment を設定しても見た目が変わらない（寄せる余白が無い）。HmiButton では `anchors.fill: parent` + `anchors.margins` で領域を Button 全体へ広げ、`horizontalAlignment: root.resolvedHAlign` 等で寄せる。enum は **人間可読な文字列**（"left"/"center"/"right"・"top"/"middle"/"bottom"）で Schema / JSON に持ち、HmiButton 側の `readonly resolved*` で `Text.AlignLeft` 等へマップする（空・不正値は中央へフォールバック＝既定外観の単一ソース。色・数値の `resolved*` と同じ集約パターン）。
- **`opacity` を Widget の公開入力名に使わない**（Task 34）。HmiButton（Rectangle）も EditableWidget（Item）も `Item.opacity` 組込みを持つため、公開入力を `opacity` にすると衝突し、`-1` センチネル（未指定）を入れると未指定 Button が透明化する。**公開入力・メタは `widgetOpacity` に統一**し、`readonly property real resolvedOpacity: widgetOpacity >= 0 ? widgetOpacity : 1.0` を導出して `opacity: resolvedOpacity` で組込みへ割り当てる。**JSON キー / `WidgetData` フィールドだけ `opacity`** とし、delegate バインド（読込）と `snapshotModel`（保存）で `widgetOpacity` ↔ JSON `opacity` をマップする（T31 の `radius`→`cornerRadius` と同型）。real センチネルは int センチネル（borderWidth）と同じ「5 箇所を揃える」則：`toJson` は `>= 0.0`、`fromJson` は `toDouble(-1)`、C++ ブリッジ save は `m.value(key, -1.0).toDouble()`、resolved は `< 0`→1.0。
- **`font.family` に空文字 `""` を束縛してはいけない**（Task 33 で実機確認）。「未指定 = 空文字」のスタイル属性パターン（上記）は色・数値では機能するが、**フォント family だけは別扱い**：`font.family: ""` は Qt/macOS で記号フォント等へ化けてテキストが文字化けする（`fontBold`/`fontItalic` 指定時はたまたま解決されたが、既定ウェイトの素のボタンで破綻した）。未指定時はアプリ既定フォントへフォールバックする `readonly property string resolvedFontFamily: fontFamily !== "" ? fontFamily : Qt.application.font.family` を HmiButton に置き、`Text { font.family: root.resolvedFontFamily }` で参照する（他の `resolved*` と同じ集約パターン）。bool（`fontBold`/`fontItalic`）は `false` 自体が「指定なし」と一致するためフォールバック不要で素直に渡せる。Schema 側 `toJson` の bool は **既定値と異なる時だけ書く**（既定 false は true のとき書き、false 省略。`fontFamily` は空のとき省略）。
- **状態別スタイル（enabled / checkable / checked）の流し方**（Task 42）。`enabled` は `opacity` と同じく `Item.enabled` 組込みと衝突するため、公開入力・EditableWidget メタは **`widgetEnabled`** に統一する（`checkable`/`checked` は `Item` に同名組込みが無いのでそのまま）。**disabled（クリック無効）は MouseArea を止めない**：HmiButton の MouseArea を `enabled:false` にすると Editor の「クリックで選択」（HmiButton.clicked 中継）まで死ぬため、淡色は `widgetEnabled`（`opacity: resolvedOpacity * (widgetEnabled ? 1.0 : 0.4)`）で見せ、**実行の無効化は SimulatorCanvas.runClickActions の冒頭で `modelData.enabled === false` を見て早期 return** する（Editor は淡色プレビューのみ・選択編集は可能）。`checked` のトグル外観は背景 `Qt.darker(resolved, 1.15)` ＋ `border.width + 2`（press の暗転とは別段で、disabled のとき press 暗転を抑止）。`checked` は binding property の選択肢（`inspectorBindingPropCombo`）にも追加し、`toggleVariable` + `Binding(property:"checked")` で変数連動できる（SimulatorCanvas で `boundValue("checked")` 追従、Task 41 の text/色と同型）。bool の保存規則は Task 33 と同じ＝**enabled は既定 true なので false のとき書く**（一律 true 書き出しだと disabled が round-trip で失われる）。
- **HmiButton の `Text` は clip しない＝ラベルは widget 幅を超えると右へはみ出す**（2026-06-09 実機ダッシュボード作成で確認）。`Text` の既定は `clip: false` なので、幅より長い 1 行テキストは Button 矩形の外（隣の widget や canvas 外）まで描画される。JSON で画面を組むときは**ラベル文字列を widget 幅に収まる長さにする**（特に左寄せの見出しバーで踏みやすい。今回ヘッダの長文がキャンバス外へはみ出した）。`elide` / `wrapMode` / `clip` は現状未公開なので、長文は幅を広げるか文言を短くする。
- **現状 Widget 種別は Button（HmiButton）1 種類のみ**で、HmiButton は `Rectangle` + `Text` + `MouseArea` の汎用「色付き四角＋文字」。スタイル属性の組合せだけで LED（正方形＋`radius`=幅の半分で円）/ ピル（`radius`=高さの半分）/ カード・パネル（大きい矩形＋`text:""`）/ ラベル（背景を地色に合わせて枠なしテキストに見せる）/ 区切り線（高さ数 px の矩形）を**擬似的に**作れる（2026-06-09、33 widget の HMI ダッシュボードを Button だけで構成し実機描画で実証）。Label / Lamp / Image 等の専用種別は Phase 5 候補（未実装）で、足せば同じ画面を少ない widget 数で素直に組めるようになる。
