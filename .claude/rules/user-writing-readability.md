# 読みやすく書く（PR・コミット・ドキュメント共通）

ユーザーが読む書き物は、すべてこのルールで書く。チャット応答の長さは [[user-response-style]]、ドキュメントの構成（Mermaid + 表）は [[feedback-docs-style]] に従う。

## 文の書き方

| ルール | 悪い例 | 良い例 |
|---|---|---|
| 1 文に 1 つのことだけ書く。1 文は 60 字前後までを目安にする | 「A を追加し（B のため）、C を D に変え、E も直した」 | 「A を追加した。B のため。」「C を D に変えた。」 |
| 括弧を入れ子にしない。括弧の中に長い補足を書かない | 「段階ガード（`.h`/`.cpp`（コメント除く）を比較）」 | 補足は別の文にする |
| 記号で文をつながない（`＝` `→` `／` `〔〕`） | 「MB-2〔読込＝`variableUpdated`→`setValue`〕」 | 「MB-2 では読み込んだ値を変数ストアへ渡す。」 |
| 結論を先に書く | 経緯 → 結論 | 結論 → 理由（必要なら） |
| 経緯・日付・PR 番号を本文に混ぜない | 「（2026-06-10 実証：PR #95 で…）」 | 経緯は [development-history.md](../../Docs/development-history.md) か `Why:` 節にまとめる |
| 太字は 1 段落に 1 か所まで | 文中の半分が太字 | 一番大事な語だけ太字にする |

## コミットメッセージ

```
<種類>: <何を変えたか（40 字前後まで）>

<なぜ変えたか。1〜3 行。件名で十分なら省略>
```

- 種類は `feat` / `fix` / `docs` / `refactor` / `test` / `chore`（フェーズタスクは `Task N:`）。
- レビュー対応の修正は `fix: <何を直したか>` とし、件名の末尾に `(Codex 指摘)` を付けない。指摘元は PR の返信に書けば足りる。
- squash マージ後は、PR のタイトルと本文が main の履歴に残る。だから PR 本文も短く書く。

## PR 本文

```markdown
## 何を・なぜ
<2〜3 行。読み手が最初の 1 行で目的を分かるように>

## 変更点
- <変更の単位で 1 行ずつ。5 個まで。ファイル名の羅列にしない>

## 確認したこと
- <ビルド・テスト・手動確認の結果>

## レビューで見てほしい点
- <1〜3 個。なければ節ごと消す>
```

- スクショがある PR は `## スクショ` を足す（[screenshot-capture](../skills/screenshot-capture/SKILL.md)）。
- 1 項目は 1 行に収める。2 行を超えるなら、PR が大きすぎないかを先に疑う。

## Why

2026-11-05 にユーザーから「全体的に文書が読みづらい。PR の内容やコミットも含めて」と指摘された。実際に読みづらかった箇所：

- AGENTS.md の「スコープ」節は、Phase 4〜11 の経緯が 1 段落に詰め込まれていた。括弧・`＝`・`→` がつながり、数千字あった。
- PR #181 の Summary は、1 文の中に括弧の入れ子と矢印が入っていた。
- PR #182 の squash コミットは、11 個の修正コミットの件名が並び、それぞれに `(Codex 指摘)` が付いていた。
