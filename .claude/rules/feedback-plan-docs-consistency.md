計画ドキュメント（`Docs/phase*-plan.md` 等）を新規作成・更新する際は、以下を必ず守る：

1. **実装側 API の制約を踏まえる**。CLI 仕様や CMake 設定を書くときは、`QCommandLineParser` / `add_test` などの実体の動作を確認してから書く。例：
   - `--e2e [<port>]` のような **optional value 表記は `QCommandLineParser` がサポートしない** → 真偽フラグ + 別の値オプションに分割する書き方にする
   - `add_test` の `DEPENDS` プロパティは **他テストの run-after 順序のみ**を制御し、ビルドターゲット依存は保証しない → ビルドは外側で担保する旨に書く
2. **未確認情報を断定形で書かない**。通信プロトコルなどライブラリ仕様は「Task X 着手時に最新 README / examples を確認」と明示的に保留する。例：Spix を「素の socket + JSON で十分」と断定したら実体は XML-RPC で、実装者が誤実装するリスクがあった
3. **複数アプリ／複数モジュールに同じ統合が必要なら Task 名に両方明記**。Editor / Simulator 等で同じ作業が要るなら「Editor 統合」だけ書くと片方が抜ける。**さらに新フェーズで新規アプリを足す時は、計画書の冒頭で「各アプリの動作環境（PC のみ / 実機のみ / 両方）」「ソース共有関係（独立 / 共有 / Shared 抽出）」を表で明文化する**。例：Phase 3-B v1（PR #36、クローズ）では「Editor JSON を i.MX8MP で描画」と書いたが「Editor 自体を i.MX に載せる」と誤読される表現だった。Editor=PC 専用、Runtime=実機専用、Simulator と Runtime はソース共有、という関係を最初に書いておけば防げた
4. **既定値（ポート / パス / バージョン番号）は plan の複数箇所で必ず揃える**。1 箇所更新したら他の箇所もまとめて確認する。Editor / Simulator のポート競合のように、同一マシン同時起動を考えるとき特に重要
5. **README の進捗表は plan 本体と同期させる**。plan の Task 名やスコープを更新したら README 進捗表も同時に更新
6. **フェーズを再スコープしたら「旧フェーズ記述」を全文書で総ざらいする**。あるスコープ（例：状態/アクション）を「次フェーズ候補」から「現フェーズに繰り上げ」のように動かしたら、それに言及する箇所が **計画書の冒頭サマリ・スコープ確定表・各アプリ役割表・Must Always/Never・進捗表に加え、CLAUDE.md（現在のフェーズ / Must Always）・AGENTS.md・README** に散在する。1 箇所だけ直すと「承認済みなのに別の箇所では未承認」「読み取り専用なのに実行を追加」のような **文書間矛盾**が残り、Codex に必ず拾われる（agent が読む主要文書間の矛盾は未承認スコープへの誤着手リスクとして P2 指摘される）。grep で旧フェーズ名・「未承認」「候補」「読み取り専用」等のキーワードを横断検索して洗い出す。
7. **役割・権限を「広げる」変更は、それを「禁ずる」既存ルールと衝突しないか確認する**。例：Simulator/Runtime に「アクション実行」を足すと、既存の「Simulator/Runtime は読み取り専用・編集系を持ち込まない」ルールと一見矛盾する → 「実行 ⊂ 可、編集 UI ⊂ 不可」と例外を明記して両立させる。
8. **完了基準とスキーマ追加項目を突き合わせる**。「X 込みで round-trip」を完了基準に書くなら、その X が Schema 追加項目リストに必ず載っているか確認（例：`checked` の round-trip を謳うのに Schema に `checked` が無い、は P2）。**読み手側（バインディング/表示）と書き手側（アクション/保存）が対で揃っているか**も確認する。
9. **bool の optional 書き出しは「既定値と異なる時だけ書く」**。一律「true のみ書く」にすると既定 true のフラグ（例 `enabled`）の `false` が保存されず round-trip が壊れる。**ショートカット割り当ては Qt の `StandardKey` 標準シーケンスと衝突しないか確認**（例：`Ctrl+D` は KDE/GNOME の `StandardKey.Delete` に含まれ削除と衝突）。

**Why:** PR #27（Phase 3-A plan 起票）で Codex から 4 ラウンド計 5 件の指摘を受けた（P1 ×2, P2 ×2, P3 ×1）。さらに **PR #68（Phase 4 拡張 plan）でも 4 ラウンド計 6 件の P2 指摘**を受けた（AGENTS.md 同期漏れ・バインディング定義欠落・`checked` 未保存・`Ctrl+D` 衝突・bool 既定値差分・フェーズ定義の文書間不統一）— 上記 6〜9 はこの実体験から追加。すべて上記のいずれかに該当する整合性・実装可能性の問題で、最初から守れば 1 ラウンドで通せていた内容。レビュー往復のコストを下げるため、計画 PR は実装 PR より丁寧に整合性を取る。

**How to apply:** `Docs/` 配下の計画系ドキュメントを書くとき。タスク表・設計指針（疑似コード含む）・ファイル配置・進捗表の **4 箇所を 1 セット**として常に整合性を確認する。**フェーズの再スコープ・承認状態の変更を伴うときは、計画書内（冒頭/スコープ表/役割表/Must ルール/進捗表）に加え CLAUDE.md・AGENTS.md・README まで grep で総ざらいして矛盾を消す**（項目 6）。実装制約に関する記述は、書く前に必要なら一度コードや Qt ドキュメントを確認してから書く。
