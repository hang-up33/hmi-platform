## 発端：前提が崩れていた

Task 23 は当初「Yocto SDK で `hmi_runtime` をクロスビルドするだけ」のはずだった。
ところが着手前に実機（i.MX8MP EVK）をシリアルで覗いたら、載っていたのは **2020 年の
`zeus` image で Qt6 が一切無い**。SDK だけ用意しても動かない——**土台から作り直し**だと判明した。

ここで仕事の性格が変わった。「1 つの小タスク」が「新 BSP（scarthgap）を丸ごとビルドして
実機 image を更新 → 同一 BSP から SDK 生成 → クロスビルド → 実機起動」という一連の大工事に化けた。
**最初の判断**：嫌がらずに前提を作り直す。ここを飛ばすと後で全部崩れる。

## 壁の連鎖と、抜け方

### 壁1: crates.io の 403（一見ネットワーク障害、実は UA ブロック）

`imx-image-full` のビルドが parsec の `do_fetch` で落ちた。最初は「一時的なネットワーク不調」に
見えた。でも**リトライしても再現**する。ログを `wget exit 8` の奥まで掘ると、crates.io（CloudFront）が
**wget の既定 User-Agent を 403 で弾いて**いた。UA を任意の文字列に変えれば 302→200 で通る。
→ `FETCHCMD_wget` に `--user-agent` を追加して解決。

**心境/教訓**：エラーメッセージ（"一時障害っぽい"）を鵜呑みにしない。**実際の HTTP 応答コードまで
掘れば原因は必ずある**。「再現するなら一時障害ではない」をまず疑う。

### 壁2: ディスク枯渇（E が小さすぎた）

`imx-image-full` のフルビルドは `tmp/work` が 41% の時点で 140GB。外付け SSD の E（233GB）では
**原理的に収まらない**。ここで **`rm_work`**（recipe 完了ごとに作業ディレクトリを自動削除し peak を
~30GB に抑える）に切替えて、E に収めた。

**心境/教訓**：「足りない」と分かったら根性で押し込まない。**ビルドの形（peak の出方）そのものを
変える**手があるかを考える。

### 壁3: GitHub スロットル

リビルド中、今度は NXP デモアプリの `gitsm` clone が `exit 128` で落ちた。並列 fetch が集中して
GitHub にスロットルされただけ——リポジトリは健在で、**リトライで通った**。

**心境/教訓**：全部が深刻な障害ではない。**「リポジトリは生きているか」を切り分け**れば、ただ待つ／
やり直すだけで済むものを見極められる。

### 壁4: 一晩動かない `diskpart compact`（遅いのか、ハングか）

SDK 生成で E が残り 3GB まで枯れた。WSL の vhdx は削除しても縮まず、`set-sparse` も `fstrim` も
効かない。最後の手段 `diskpart compact vdisk`（228GB）が **「10% 完了」で一晩止まったように見えた**。
「これ本当に進んでる…？ ハングして無駄に待ってるだけじゃ？」という不安が一番強かったのはここ。
でも翌朝には **完了して 52GB 戻っていた**。ただ遅かっただけだった。

**心境/教訓**：**「遅い」と「ハング」は違う**。非破壊操作（readonly attach での compact）なら、
不安でも待つ判断が正解になることがある。疑わしい時はまず「本当に動いているか（ディスク I/O が
出ているか）」を確認してから、待つ／止めるを決める。

### 壁5: full SDK が onnxruntime で詰まる（過剰を疑う）

ディスクをあれだけ苦労して空けた直後、今度は full SDK の `do_populate_sdk` が **`onnxruntime-dbg`
（692MB の ML デバッグ deb）の dpkg 展開で失敗**した。心が折れかけたが、ここで一歩引いて気づいた——
**「Qt6 のクロスビルドに ML も opencv も要らない」**。フル SDK ではなく Qt6 だけの
`meta-toolchain-qt6` に切替えたら、あっさり通った。

**心境/教訓**：問題にぶつかったら「どう直すか」の前に **「これ本当に要るんだっけ？」と引く**。
過剰な構成を削ると、問題そのものが消えることがある。最短より「正しい大きさ」。

### 壁6: 実機が新 image で起動しない

焼いた microSD から起動せず、**また 2020 年の zeus が立ち上がった**。eMMC 優先で SD を見ていなかった。
ブートモードスイッチ **SW4 を `0011`（SD 起動）** に変えたら scarthgap が起動した。

**心境/教訓**：ソフトが正しくても、**ハード側の前提（boot 順）**で全部止まる。一次情報（起動ログ）を
見て切り分ける。

### 壁7: 実機への転送（小さい壁を一個ずつ）

最後に転送で細かい壁が連続した：`sshd.service` が無い（実は **socket-activated**）、新しい scp が
**SFTP 既定で失敗（`-O` 必須）**、LAN 直結で **link-local（169.254）** になり WSL から届かない
（Windows 母艦から scp）、weston は **root（uid 0）** で動いていて socket は `/run/user/0/wayland-1`。
**一個ずつ潰した。**

**心境/教訓**：複合的に見える障害も、**分解すれば一個ずつ**。焦って全部同時に直そうとしない。

## ゴール

`/tmp/hmi_runtime --open /tmp/project.json` を叩いて、実機の画面に **3 つのボタンが出た瞬間**——
"Hello i.MX8MP" / "scarthgap + Qt6 6.8.1" / "hmi_runtime cross-built OK"。
Editor が出す JSON が、PC を一切経由せず実機 i.MX8MP の Qt6 で描画された。

## まとめ：抜けるために効いた 3 つの姿勢

1. **推測で叩かず、根本原因を診断する。** UA の 403 も、ext4 が vhdx を伸ばす挙動も、sshd の
   socket-activation も、「症状」ではなく「機構」を見たら抜けられた。再現する障害は一時障害ではない。
2. **過剰を疑って引く。** full SDK → 軽量 SDK のように、問題の手前で「そもそも要るか」を問うと、
   直すより消す方が速いことがある。最短ではなく「正しい大きさ」を選ぶ。
3. **可逆性を確保してから壊す。** distro relocate は export→検証→unregister の順、compact は
   readonly attach。「戻せる」状態を作っておくと、不安な操作にも踏み込める。

そして全体を通して——**諦めないが、固執しない**。前提（vendor SDK 期待）も、手段（full SDK）も、
要所で柔軟に捨てた。捨てる勇気と、待つ忍耐（一晩の compact）の両方が要った。
壁は毎回「詰んだか」に見えたが、分解して一個ずつ見れば、必ず次の一手があった。
